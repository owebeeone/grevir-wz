## Findings

**P1 — Named target examples bypass the required start state machine.**
Location: [start.hpp](/Users/owebeeone/limbo/grevir-wz/grevir-core/src/grevir/interrupt/start.hpp:24), [AVR board](/Users/owebeeone/limbo/grevir-wz/docs/examples/interrupt-avr/avr_app_base.hpp:21), [ESP32 board](/Users/owebeeone/limbo/grevir-wz/docs/examples/interrupt-esp32/esp_app_base.hpp:21), and both `.ino` setup functions. Trigger: instantiate `Application<GrevirApplication>::start()` for either published board, or call either example’s `setup()` more than once or after an installation failure. Scope: AVR and classic ESP32 target integration. Classification: correctness defect introduced by this implementation. Neither board supplies `StartPolicy`, `mask_owned`, `configure`, `setup_modules`, `settle_pending`, `enable_owned`, or `cleanup`, so the runner cannot be instantiated. The examples call `detail::install_bindings` directly and therefore have no settled `StartResult`, one-shot guard, or terminal cleanup behavior. The ESP32 board additionally configures the timer *inside* `install`, whereas the specified order configures owners before installing entries. Implement the board lifecycle and use `Application<Spec>::start()` in both examples. Closure test: compile both named targets through the runner and assert initiated/waited/replayed success and terminal failure, including masking and cleanup after registration failure.

**P2 — The CMake consumer treats marker existence as readiness without validating its contents or outputs.**
Location: [GrevirInterruptBindings.cmake](/Users/owebeeone/limbo/grevir-wz/grevir-core/cmake/GrevirInterruptBindings.cmake:59), [transaction.py](/Users/owebeeone/limbo/grevir-wz/grevir-core/tools/grevir_irqgen/transaction.py:38), [emit.py](/Users/owebeeone/limbo/grevir-wz/grevir-core/tools/grevir_irqgen/emit.py:66). Trigger: a previously generated directory retains a ready marker while a generated header or source is replaced, corrupted, or comes from another emitter revision with the same plan fingerprint. Scope: CMake host build transaction and all backends. Classification: correctness defect introduced by this implementation. The transaction validates only five marker fields immediately after emission; the CMake dependency later checks only the marker pathname. `output_identity`, protocol, and emitter are recorded but never checked before compilation, while generated C++ checks only the plan fingerprint between header and source. Thus marker existence does not establish the promised complete current output set. Add a consumption-time validation step that checks marker attempt and target/compiler/emitter/protocol identities and hashes the declared outputs before firmware compilation; retain strict C++ plan checks. Closure test: start with a valid set, alter each byproduct or marker identity independently, and verify the build rejects it before compiling the binding unit.

**P3 — ESP32 registration failure is reported as cleanup failure even when there is no handle to release.**
Location: [timer_group0_timer0.hpp](/Users/owebeeone/limbo/grevir-wz/grevir-arduino-esp32/src/grevir/arduino_esp32/timer_group0_timer0.hpp:26) and [timer_group0_timer0.hpp](/Users/owebeeone/limbo/grevir-wz/grevir-arduino-esp32/src/grevir/arduino_esp32/timer_group0_timer0.hpp:64). Trigger: `esp_intr_alloc` fails, then the caller invokes `cleanup()`. Scope: classic ESP32 backend. Classification: correctness defect introduced by this implementation. `install` disables the module and leaves `handle_ == nullptr`, but sets `failed_`; `cleanup()` then returns `!failed_`, falsely indicating a cleanup failure. Keep registration failure state separate from release failure state. Closure test: inject allocation failure and assert registration failure with successful no-handle cleanup; separately inject `esp_intr_free` failure and assert cleanup failure with retained handle.

## Invariant analysis

The `plan`/`emit` sequence does invalidate the old marker first, uses temporary files and atomic replacement for JSON/header/source, and publishes the marker last. A failed generation command therefore blocks the dependent CMake target in that invocation. The Arduino wrapper likewise clears its firmware marker before building and publishes it after private export. These source-level observations do not establish crash durability or physical behavior.

The generated per-source C-linkage guard is read in the installer and has a strong definition, so ordinary linking should retain it and reject duplicate binding units for the same source. AVR masking and pending preservation are explicit in the adapter; ESP32 masking, handle retention, callback affinity, and interrupt-context safety still require the named-target error and hardware checks prescribed by the plan. S2/S3, RISC-V, arbitrary interrupts, and silicon validation remain outside this review.

**P3 — Task ownership can change independently of an active queue.** [MainLoopContext::bind()](/Users/owebeeone/limbo/grevir-wz/grevir-arduino-esp32/src/grevir/arduino_esp32/event_context.hpp:41) writes one backend-wide static task handle; [prepare()](/Users/owebeeone/limbo/grevir-wz/grevir-core/src/grevir/event/queue.hpp:35) calls it before taking the queue lock. For example, task A can prepare and begin dispatching a queue, then task B can directly call the public `prepare<Spec>()`: B becomes the owner while A’s already admitted dispatch can still invoke a callback. A later dispatch by A returns zero. The same shared owner field could affect separate application specs using this context class. This is an **introduced ESP32 ownership limitation**, outside the checkpoint’s one-start-from-`setup()` example; it is not a demonstrated failure of that path. The impact is misplaced or stalled callbacks if rebinding is allowed during an active queue. Bind ownership per application and define a guarded stop/rebind transition, or reject preparation while active. A closure test should prepare on A, pause A inside a callback, attempt preparation on B, then verify that every callback executes only on the declared owner and that queued work remains dispatchable.

**Invariant analysis.** Task and ISR publishers enter the same [port mux](/Users/owebeeone/limbo/grevir-wz/grevir-arduino-esp32/src/grevir/arduino_esp32/event_context.hpp:17) through their matching critical-section APIs. Under that lock, publication writes the record and Elide mark before increasing the count; dequeue clears the mark before releasing the lock and invoking the callback. Thus a firing during a callback may enqueue again. Stream appends each accepted firing, while full capacity sets the sticky overrun flag without claiming delivery. The [dispatching guard](/Users/owebeeone/limbo/grevir-wz/grevir-core/src/grevir/event/queue.hpp:65) rejects nested or competing dispatch. These are source-level synchronization conclusions, not measured cross-core behavior.

In the selected example, [startup](/Users/owebeeone/limbo/grevir-wz/grevir-core/src/grevir/interrupt/start.hpp:26) prepares the queue before enabling its source; failure masks the source and stops the queue. An ISR racing with stop either publishes before records are cleared or observes `not_ready` afterward. [TimerStartPolicy](/Users/owebeeone/limbo/grevir-wz/grevir-arduino-esp32/src/grevir/arduino_esp32/timer_group0_timer0.hpp:110) executes startup once, so a replayed start does not rebind the task. The example calls startup from `setup()` and dispatch from `loop()`, both on Arduino’s loop task.

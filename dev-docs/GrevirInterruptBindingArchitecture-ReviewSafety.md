## 1. Findings

### [P2-1] Failed setup leaves acquired ESP32 registrations without a defined recovery state

**Location:** Architecture lines 267–279 and 294–301. **Scope and classification:** Classic ESP32 runtime recovery; design defect introduced by this specification.

The lifecycle installs entries one source at a time, records handles, and reports an allocation error, but requires only that “affected sources” remain disabled. It does not say whether already acquired handles are freed, whether the start state becomes permanently failed, or whether a later `start()` may retry. With two sources, registration of the first can succeed and the second can fail. The first callback and its allocator resource remain acquired while setup reports failure. A retry can then encounter its own prior registration; a permanent failed state can retain the handle for the firmware lifetime. Neither outcome is ruled out by masking the source. Concurrent callers also need to observe the settled failure state before any retry is admitted.

This violates the promised one-registration lifecycle and leaves a concrete stuck resource state. Specify an all-source rollback on failure, or an explicit terminal failure state with defined handle ownership and no retry; define how concurrent callers receive that result. A closure test should inject failure on the second of two mock registrations, call `start()` concurrently and again afterward, and verify the chosen recovery rule, handle count, masked state and caller results. The ESP32 adapter then needs a named-target allocation-failure check; host tests alone cannot establish its runtime behavior.

### [P2-2] The generated output set has no specified atomic publication boundary

**Location:** Architecture lines 188–200, 238–244, 256–263, 336–353 and 384–408. **Scope and classification:** Shared build integration for mock, AVR and ESP32; recovery and mixed-version design defect introduced by this specification.

The plan command writes JSON before the emit command writes a header and source. Emission completes files in a temporary directory, then “publishes” them, but the text defines no single atomic promotion of the JSON, header and source as one version. Publishing files individually permits interruption after replacing one output while older siblings remain. A plan fingerprint checks correspondence to the application plan; it does not by itself prove that two files generated by different emitter versions belong together when the plan is unchanged. The assertion that a build “never pairs” files from different emissions therefore lacks a mechanism.

This threatens the stated fail-closed stale-artifact guarantee across an interrupted generation or tool upgrade. Specify a versioned output directory or equivalent atomic manifest boundary that consumers select only after the complete set is verified; make emitter/protocol identity part of that selection. A closure test should interrupt publication after each possible file promotion with valid older outputs present, then rebuild and verify that no mixed set is compiled or exported and that recovery regenerates a complete set.

### [P2-3] Startup acknowledgement can discard a demanded pending event

**Location:** Architecture lines 269–273, 281–287 and 294–307. **Scope and classification:** Shared interrupt-delivery contract with target-specific acknowledgement policy; correctness defect permitted by the specification.

The specified order initializes dependent modules while sources are masked, installs entries, then clears or acknowledges pending conditions before enabling. A module or external device can assert a source after initialization but before that clear. For a latched event, an acknowledgement that clears its pending bit consumes it without dispatching the requested handler. The document delegates acknowledgement to the backend but gives no rule for whether such an event must be delivered, retained, or explicitly discarded. The mock tests call for observing acknowledgement, yet do not require an event injected in this window to have a defined outcome.

Define startup pending-event semantics for each offered event. If delivery is required, preserve or dispatch the pending snapshot before enabling and acknowledge only the consumed condition. If startup events are intentionally discarded, state that contract and require the owner to establish a quiescent precondition before dependent modules can rely on the source. A closure test should raise each offered mock event between module initialization and entry enabling, then assert the specified delivery or discard behavior; named AVR and ESP32 backends must implement the corresponding status and acknowledgement policy without inferring silicon behavior from the mock.

## 2. Invariant analysis

The static one-source/one-owner rule resisted the review’s direct attacks: lines 134–150 require exact demand-to-binding equality, one owner and entry per physical source, distinguishable selectors for shared-source events, and rejection of exclusive-entry conflicts. Lines 246–254 add a generated installer and source guard, while lines 256–261 compare a strict build against the current plan. Those rules address missing bindings and stale application plans at compile or link time.

They do not settle the three runtime and build-transition windows above. In particular, a masked source is still capable of holding a registration handle or a pending status bit, and matching plan fingerprints do not establish atomic publication of an output set. External code outside Grevir remains expressly outside compile-time exclusivity; I did not treat that stated boundary as a finding.

## 3. Risks and next action

The proposed transport, target emitters and Arduino/CMake integration remain implementation gates, and silicon validation is deferred. Their absence was not treated as a defect in this design review. The next action is to amend the specification with explicit failed-start recovery, generated-set publication, and startup pending-event contracts, then re-review those counterexamples on the revised blob.

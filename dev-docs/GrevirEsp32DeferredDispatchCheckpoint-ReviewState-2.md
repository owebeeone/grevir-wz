**Changed-range state analysis — NEW ARCHITECTURAL root cause: none found.** The core range makes preparation conditional on inactive state, checks ownership at dispatch admission, and selects task versus ISR guards for publication. The ESP32 range supplies one port mux and per-`Spec` owner storage. AVR and host lock aliases preserve their existing critical-section behavior. Root example and documentation changes route the generated interrupt into the queue and drain it from `loop()`. The selected [TimerStartPolicy](/Users/owebeeone/limbo/grevir-wz/grevir-arduino-esp32/src/grevir/arduino_esp32/timer_group0_timer0.hpp:110) executes startup once, so replay does not rebind the owner.

**P0–P3 findings: none.** Capturing `xTaskGetCurrentTaskHandle()` before the guard does not create an owner race for the running task: its handle remains its identity if it migrates cores, while bind and comparison occur under the same lock. An ISR or task publication serializes record and Elide-mark changes with dequeue. Dispatch clears the mark before calling the callback outside the lock, permitting a firing during the callback to enqueue again. `dispatching_` prevents nested or competing callbacks; stop clears queued records, and preparation cannot transfer ownership until an admitted dispatch finishes. A failed `prepare()` reports `event_context_failed` without stopping a queue it did not acquire. Stream retains each accepted record; a full queue sets overrun without claiming delivery.

**Remaining limits.** Host mutex tests and target compile/link do not exercise ESP32 cross-core timing, physical interrupt behavior, or task-handle lifetime. A stop issued during a callback can return while that already-admitted callback finishes; the implementation prevents a new owner from preparing during that interval. Silicon validation and the explicitly deferred targets and services remain unclaimed.

**Evidence base.** Read-only review of each specified `HEAD^..HEAD` diff, the root checkpoint draft, the governing cross-MCU, ESP32, AVR and declarative-integration policies, and the existing probe, plan, emitter, startup and backend call paths. **P2 — ESP32 main-loop ownership is optional in an active deferred plan.** In [queue.hpp](/Users/owebeeone/limbo/grevir-wz/grevir-core/src/grevir/event/queue.hpp:36), `prepare()` binds the task only if `Board::MainLoopContext` exists; [dispatch()](/Users/owebeeone/limbo/grevir-wz/grevir-core/src/grevir/event/queue.hpp:67) likewise checks the calling task only if that alias exists. Yet [DeferredContextPlan](/Users/owebeeone/limbo/grevir-wz/grevir-core/src/grevir/interrupt/binding.hpp:164) requires only capacity and `EventLock`, and the generated strict checks compare only capacity and lock policy. **Trigger:** remove the `MainLoopContext` alias from an otherwise unchanged classic ESP32 board, such as [the example board](/Users/owebeeone/limbo/grevir-wz/docs/examples/interrupt-esp32/esp_app_base.hpp:25). The deferred plan still selects `main_loop`, the ISR still posts, and `dispatch()` called by any FreeRTOS task may execute the callback. **Scope:** shared queue contract as instantiated by the classic ESP32 backend. **Classification and provenance:** correctness defect introduced by this checkpoint’s optional ownership branches. **Impact:** the promised Arduino `loopTask` execution context is no longer enforced, with no plan or stale-output failure to expose the change. **Correction:** make task ownership a required, validated part of the selected ESP32 deferred-context policy and its plan identity; retain a deliberately explicit policy for targets that have no task restriction. **Closure test:** a negative target compile with the ESP32 context alias omitted must fail, and a positive runtime or suitable host policy test must show that a foreign task cannot consume records.

**Invariant analysis.** The catalogued `on_event<PeriodElapsed>()` specialization creates demand through the existing probe. The plan carries handler, route, capacity and lock identity; the emitter’s generated callback calls `dispatch_bound_interrupt`, which uses `post_from_isr` for deferred delivery. Startup prepares the queue before source enablement and stops it on failure. The new ESP32 guards use one `portMUX_TYPE`, with task and ISR entry points selected by the corresponding queue calls; callback invocation occurs after the guard exits. The example supplies the context alias and polls from `loop()`. These source-level observations support the intended selected path, but do not repair the missing API gate above.

**Risks and limits.** The ESP32 context owner is a process-wide static task handle, so multiple independently started applications using this policy could overwrite one another’s owner; that composition is outside this checkpoint’s demonstrated single-application timer slice. The guide describes ESP32 `Stream` support from the shared implementation, while the stated ESP32 target compile/link evidence covers `Elide` only. Cross-core runtime behavior, physical interrupts, S2/S3/RISC-V, named contexts, software events, sleep/notification and general timer-owner remediation remain deferred as specified.
